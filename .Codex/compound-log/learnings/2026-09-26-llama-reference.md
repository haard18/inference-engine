The new `scripts/llama-reference.py` runs the project probe and `llama-completion` with greedy selection, eight requested tokens, one warmup per binary, and five alternating measured invocations. Each invocation starts a new process and loads the model. With Metal, both engines produced the same text and digest. Median wall times were 0.268 s for this engine and 0.160 s for llama.cpp. With CPU, median times were 0.571 s and 0.152 s, but the generated text differed. These timings cannot stand in for warm server throughput or concurrency results.

For direct numerical diagnosis, a temporary program used the llama.cpp C API to read all 49,152 first-token scores from the same prompt. Against the project's CPU scores, llama.cpp Metal had mean absolute error 0.00084 for Q4_K_M and 0.00161 for Q8_0. Both chose the same highest token as this engine. A separate three-trial Q8_0 Metal run also produced matching eight-token text. The Q4_K_M llama.cpp CPU scores had mean absolute error 1.15 and chose a different highest token. The project scores continue to match the independent NumPy calculation. llama.cpp's CPU quantized vector operations use quantized activations; different numerical paths are a plausible explanation, but this run does not prove that this is the only cause.

The earlier assumption that a different llama.cpp completion proves an engine decoding fault was too strong. Compare prompt token IDs and score arrays before changing the decoder.
