# 2026-09-26 - Capacity-aware whole-request routing

The peer API now reports a bounded snapshot containing model ID, readiness, active work, free queue slots, queue size, context length, and maximum completion length. The snapshot is available only through the mutual TLS peer listener. The coordinator reads snapshots concurrently when its local worker has a backlog or is unavailable. It considers only ready peers that accept the requested model and token lengths and have free queue space. It selects a peer only when that peer has less work than the local worker.

The coordinator forwards the original chat request through a certificate-authenticated HTTP connection. It forwards response headers and bodies without collecting the whole completion, so streamed responses remain streamed. Local and peer routes share the same bounded worker queue on each device. A peer whose connection or capacity check fails gets a five-second cooldown. A failed peer request before response headers falls back to the local worker within the original deadline. A peer 429 or 503 response also falls back before its response reaches the caller. A 503 may occur after model work began, but inference has no external side effects and no output from that attempt has escaped to the caller.

The first client test failed because its saved peer address was a fixture port while the test listener used an ephemeral port. After assigning the actual listener address, a real-model test verified capacity lookup, ordinary and streamed chat forwarding. A two-device test killed the local worker, received a real-model response from the peer, then stopped the peer and received HTTP 503. Another test held a fake local worker busy and showed that the next request completed on an idle real-model peer.

The capacity snapshot is a point-in-time hint. Another request may fill the peer queue before forwarding; the peer still enforces its bound and returns 429. Ordinary peer responses are collected before being sent to the caller, so an incomplete body can still fall back locally. Streamed responses remain incremental. If a peer stream ends without its completion marker, the coordinator emits a `peer_stream_lost` SSE error and closes it without replay. A truncated-response test verified both the ordinary and streaming cases. Load measurement, conversation reuse, and model splitting remain open.
